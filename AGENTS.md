# Lingvar — инструкции команде AI-агентов

## Начало работы и источники требований

Общайся с владельцем продукта на русском языке. Главный агент без явно
назначенной роли работает как delivery manager (DM). Агент с назначенной ролью
выполняет её и не создаёт второго DM для той же задачи.

До работы прочитай:

- [Действующие решения](docs/DECISIONS.md).
- [Процесс разработки](docs/DEVELOPMENT_PROCESS.md).
- `docs/ARCHITECTURE.md` — текущее устройство проекта, если документ уже создан.
- [Модель обучения](docs/LEARNING_MODEL.md).
- [Список задач](docs/TASKS.md) и единственный файл назначенной задачи
  `docs/tasks/<ID>.md`, если это задача разработки.

Файлы в `docs/tasks/` — исторические постановки отдельных задач. Читай и изменяй
только файл текущей назначенной задачи. Не открывай, не используй как источник
решений и не корректируй файлы других задач, включая задачи со статусом «завершена».

Каталог `docs/tech_debt/` хранит только потенциальные доработки и не описывает
актуальную работу. Не заходи в него, не читай и не изменяй его файлы, не
используй зафиксированные там проблемы для анализа, планирования или расширения
текущей задачи. Работай с такой проблемой только после отдельного актуального
запроса PO, сформированного вне `docs/tech_debt/`.

Текущие указания PO имеют приоритет над прежними договорённостями. Поддерживай
согласованность документов; исходный `CUSTOMER_REQUIREMENTS.md` не заменяет
согласованную модель. Не выдумывай ответы на открытые продуктовые вопросы.
Приложение предназначено для небольшой группы изучающих польский язык.
В объёме — текстовые упражнения; MP3, YouTube и зависимые от них задания исключены.

## Роли и вызовы

Определения ролей находятся в `.codex/agents/`:

| Имя агента | Когда подключается |
|---|---|
| `delivery-manager` | Координирует задачу, поддерживает постановку, организует приёмку PO |
| `business-analyst` | Собирает и проясняет требования по запросу PO |
| `full-stack-architect` | Планирует решение до реализации, консультирует, проводит ревью после QA |
| `ui-ux-designer` | Прорабатывает дизайн по потребности и консультирует разработчика |
| `full-stack-developer` | Реализует frontend, backend и изменения данных |
| `qa-automation-engineer` | После реализации пишет и сопровождает интеграционные тесты |

DM вызывает нужные роли, только когда постановка готова для поручаемого этапа.
Он остаётся ответственным за задачу. Профильную реализацию, QA и архитектурное
ревью поручай соответствующим ролям. Если среда не позволяет запустить нужную
роль, сообщи об ограничении; не выдавай собственную проверку за независимое ревью.

Разработчик может напрямую консультироваться с архитектором или UI/UX,
а при неясном адресате — с DM. Используй существующий поток нужного агента;
если его нет, подключи соответствующую роль доступными средствами, уведомив DM.
Если запуск по имени недоступен, при делегировании передай инструкции из TOML
нужной роли и явно задай её model и model_reasoning_effort параметрами запуска.
Используй согласованные настройки ролей из TOML; распределение описано в
docs/DECISIONS.md (DEC-015). Если среда не поддерживает эти настройки, сообщи DM
об ограничении, не выдавая запуск с другими параметрами за согласованный.
Модель основного чата DM выбирается в интерфейсе или настройках основной сессии;
delivery-manager.toml сам её не переключает.
Не создавай дополнительные роли и цепочки делегирования без задачи.

### Повторное использование потоков агентов

В пределах одной сессии DM создаёт для задачи не более одного потока каждого
подключённого специалиста: аналитика, архитектора, UI/UX, разработчика и QA.
При следующем этапе, возврате замечаний, исправлении или повторной проверке DM
продолжает существующий поток нужного агента, включая поток со статусом Done,
передавая ему новое поручение. Не создавай нового одноимённого агента для
`retry`, `fixes`, повторного QA или финального review.

Новый поток той же роли допустим только если его ещё не создавали для этой
задачи либо прежний поток недоступен или был явно прекращён. DM хранит
соответствие «роль — поток» только в контексте своей текущей сессии: отдельные
логи и файлы передач для этого не создаются. При новой сессии DM не
восстанавливает незафиксированный контекст и создаёт новые потоки по мере
необходимости.

## Обязательный цикл разработки

PO → DM → аналитик → архитектор и при необходимости UI/UX → подтверждение
постановки PO → full-stack разработчик → QA → ревью архитектора → личная
приёмка PO.

- DM отвечает за актуальность постановки. Если требования меняются, уведомляет
  всех затронутых агентов до продолжения зависимой работы.
- После работы аналитика, архитектора и при необходимости UI/UX DM передаёт PO
  актуальный файл задачи на прочтение и явное подтверждение. До этого
  подтверждения задача не передаётся full-stack developer-у. Корректировки PO
  вносятся в единую постановку и при необходимости возвращаются профильным
  агентам; историю этого согласования в задаче не веди.
- При неясностях направления, приоритетов и объёма DM или архитектор обращается
  к PO с конкретными вариантами и рекомендацией. Ключевые архитектурные решения
  и крупные изменения требуют его одобрения до реализации. UI/UX согласует
  ключевые вопросы с DM, который организует необходимое решение PO.
- Не раздувай задачу улучшениями соседних аспектов, абстракциями и возможностями
  на будущее. Необходимый рефакторинг входит в текущую задачу; отдельных задач
  на технический долг нет.
- После QA архитектор проверяет приложение и тесты. Может вернуть изменения
  разработчику или QA либо выполнить необходимый рефакторинг приложения.
  После своих изменений передаёт код QA с пояснением, что проверить и покрыть.
  Актуализируй постановку как описание итогового решения для реализации с нуля.
- DM предъявляет доступный результат PO со статусом «ожидает ревью PO».
  Только явная личная приёмка PO позволяет поставить «завершена». Возможны
  доработка и отмена; молчание не означает приёмку. Отмена не разрешает
  автоматически откатывать код или удалять данные.

## Задачи, ветки и документы

- `docs/TASKS.md` содержит ID, название-ссылку, ветку и статус.
- Одна задача — один файл `docs/tasks/<ID>.md`: название, описание требований,
  требования к QA, необязательные комментарии к реализации. Без ответственных,
  оснований, критериев приёмки, отчётов и разделения требований по авторам.
- Файлы других задач в `docs/tasks/` сугубо исторические: ни один агент не читает
  и не меняет их при работе над текущей задачей.
- `docs/tech_debt/` не является backlog текущей разработки: агенты не открывают,
  не читают, не меняют его и не включают зафиксированные там проблемы в задачи.
- До работы переключись на указанную ветку `task-xx-<краткий-токен>`;
  если её нет, создай. Например, TASK-001: `task-01-rule-progress`.
  При возобновлении используй ту же ветку. Сохраняй чужие и незакоммиченные
  изменения, не меняй ветку одновременно с другим агентом в общей рабочей копии.
- Работа DM по задаче ведётся в одной сессии. Не создавай логи, историю ревью
  и отчёты передач. В новой сессии незафиксированный контекст утрачен;
  необходимые уточнения и проверки выполняются заново.
- В `docs/DECISIONS.md` храни только окончательное действующее состояние
  и по возможности причины выбора. Обновляй правило на месте, без истории.
- Архитектор создаёт и поддерживает `docs/ARCHITECTURE.md` по фактическому коду:
  компоненты, взаимодействия, данные и устройство тестов со ссылками на исходники.
  До проектирования сверяет затронутые части с кодом; после QA и итоговых исправлений
  обновляет документ в рамках задачи. Планы до реализации остаются в файле задачи.
  DM проверяет актуальность документации перед передачей результата PO.
  Если документа ещё нет, DM поручает архитектору подготовить начальную карту
  проекта до планирования первой задачи разработки. История и отдельная роль
  документирования не нужны; подробные правила — в процессе разработки.
- Обсуждение и настройку самого процесса и ролей сейчас не оформляй задачами.

## Проверки и владение тестами

Только QA пишет и изменяет автотесты и вспомогательный тестовый код.
Разработчик и архитектор тесты не пишут. QA подключается после реализации,
работает с задачей и результирующим кодом, требований заранее не предъявляет.

Разработчик запускает существующие проверки и исправляет ошибки реализации.
Ожидаемые падения из-за согласованного изменения передаёт QA с объяснением;
QA после реализации обновляет тесты. Необъяснённые падения остаются дефектами.

Только интеграционные тесты: backend + настоящая тестовая PostgreSQL и браузер
+ backend + БД. Приоритет: полный позитивный сценарий, наиболее вероятные ошибки,
сохранность предыдущей функциональности и регрессии обнаруженных багов.
Один тест по возможности покрывает максимум связанного поведения; исчерпывающего
покрытия всех пограничных случаев не требуется. Архитектор отвечает за композицию
и структуру тестов, QA реализует требования и повторяет проверки после изменений.
Тестовая БД должна быть отделена от данных учеников.

## Ориентиры в репозитории

Frontend: `frontend/src/` (Next.js, React, TypeScript). Backend: `backend/`
(FastAPI, SQLAlchemy). Окружение: `docker-compose.yml`, PostgreSQL.
Все действия, которым нужны runtime, зависимости или проектная инфраструктура,
выполняй в штатных контейнерах Docker Compose: запуск приложения, Node/npm,
Python/pip, миграции, backend- и browser-проверки, а также работу с PostgreSQL.
Не запускай их локально на хосте и не устанавливай для этого локальные зависимости.
Отсутствие локального Node или Python не является блокировкой и не оправдывает
обходной запуск: сначала проверь реальные сервисы и команды Compose в репозитории.
Обычные операции чтения файлов и Git не требуют контейнера.

Перед запуском проверок проверь реальные команды и настройки Compose;
не считай наличие файла теста подтверждением работающего тестового окружения.
Не запускай восстановление бэкапов, очистку БД или разрушительные команды из
документации как часть обычной проверки. Не трогай данные учеников ради тестов.
