# Исправление регистрации нового ученика

## Описание требований

Исправить регистрацию нового ученика, не меняя модель пользователей, вход,
JWT, роли, административный API или дизайн приложения.

- Существующая форма `/signup` передаёт введённые `username`, `email` и `password`
  в фактически поддерживаемый endpoint `POST /users/register` по существующему
  контракту `UserCreate`: JSON с этими тремя полями, без `confirmPassword`.
  Использовать уже заданный в `frontend/src/lib/api.ts` адрес регистрации,
  не дублировать URL в странице маршрута.
- После успешного создания пользователя сохраняется текущий сценарий: переход
  на `/login` с понятным сообщением о создании учётной записи и предложением
  войти. Регистрация не выполняет автоматический вход.
- Если username или email уже занят, форма показывает понятное сообщение об
  этом. Backend для обоих случаев возвращает HTTP 400 с общим `detail`
  `Username or email already registered`; различать занятое поле по этому
  ответу не требуется. При любой другой ошибке API, включая ошибки валидации
  и ответ без пригодного текстового `detail`, форма показывает понятное
  сообщение вместо технического объекта или пустого текста. При недоступности
  API также показывать понятное сообщение.
- При ошибке не сбрасывать введённые значения формы, включая подтверждение
  пароля; локальная проверка совпадения паролей сохраняется. После завершения
  запроса снимается состояние загрузки, чтобы пользователь мог исправить данные
  и повторить отправку.
- Не исправлять другие найденные расхождения frontend и backend за пределами
  регистрации.

## Требования к QA

Расширить существующий интеграционный сценарий backend на отдельной тестовой
PostgreSQL с синтетическими данными: `POST /users/register` с валидными
`username`, `email`, `password` возвращает успешный ответ и создаёт пользователя;
повторный запрос с теми же данными возвращает HTTP 400 и понятный `detail`;
после него прямой запрос к тестовой БД находит ровно одного пользователя с
этими username/email. Использовать существующие защитные фикстуры
`backend/tests/conftest.py` и сценарий API после миграции в
`backend/tests/test_migrations.py`, не строить проверку на порядке запуска
независимых тестов и не обращаться к БД учеников.

При наличии надёжного изолированного контура выполнить браузерный сценарий
`/signup` с backend на отдельной тестовой PostgreSQL: отправка вызывает
`POST /users/register`, после успеха открывается `/login` и виден текст
подтверждения; при повторной отправке занятых данных видна ошибка и сохраняются
все четыре поля формы. Проверить также одну ошибку API, не связанную с
дубликатом, либо недоступность API: сообщение остаётся понятным, значения формы
сохраняются. Создавать отдельный browser-контур ради этой задачи не требуется;
ручную сквозную проверку не считать заменой backend-теста.

## Комментарии к реализации

Маршрут `/signup` реализован в `frontend/src/app/signup/page.tsx`; в
`frontend/src/components/pages/SignupPage.tsx` есть дополнительная реализация,
которая не является точкой входа App Router. `frontend/src/lib/api.ts` уже
содержит правильный `API_ENDPOINTS.register` и метод `ApiService.register`;
подключить маршрут к этому клиенту и при необходимости ограниченно улучшить
обработку ошибок регистрации в методе. Текущее хранение значений и локальная
проверка подтверждения находятся в `SignupForm`; состояния ошибки/загрузки и
успешный переход — в странице. `LoginPage` читает параметр `message`,
`LoginForm` отображает подтверждение. Backend-роутер, пользовательская ORM,
схема PostgreSQL и миграции для этого исправления не меняются.
