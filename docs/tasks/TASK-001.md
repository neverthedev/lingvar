# Версионированные миграции PostgreSQL

## Описание требований

Внедрить управляемое версионирование схемы PostgreSQL вместо создания схемы
через SQLAlchemy `create_all` при штатном запуске. Предпочтительный инструмент —
Alembic; его применимость к текущему коду подтверждена статическим анализом.
Конкретное решение приведено ниже.

- Начальная миграция должна создавать полную текущую схему Lingvar в новой пустой
  PostgreSQL. Она становится точкой отсчёта для последующих изменений схемы.
- Для существующей БД должен быть предусмотрен отдельный безопасный переход под
  управление миграциями с сохранением данных. Базовая версия регистрируется как
  уже применённая только после успешной проверки фактической схемы против
  начальной миграции, а не против текущих ORM-моделей.
- Предварительная проверка существующей БД не изменяет её схему, данные или
  таблицу версий. Она должна выявлять существенные отличия структуры, влияющие
  на применимость начальной миграции: состав таблиц и колонок, типы и
  обязательность колонок, ключи, внешние ключи, уникальные ограничения, индексы,
  значения по умолчанию и прочие объекты, которые задаёт начальная миграция.
  При отличиях команда перехода завершается с понятной диагностикой каждого
  расхождения и не регистрирует базовую версию.
- В эксплуатационной инструкции должен быть указан безопасный дальнейший порядок
  для БД с расхождениями: сначала отдельно подготовить и проверить изменение,
  сохраняющее данные, затем повторить проверку и регистрацию версии. Автоматически
  исправлять неизвестную существующую схему в рамках перехода нельзя.
- Штатный запуск применяет согласованный порядок миграций до запуска приложения
  вместо `create_all`. Если соединение с БД, проверка состояния миграций или
  обновление схемы завершается ошибкой, приложение не должно продолжать работу
  как будто схема подготовлена.
- Краткая эксплуатационная инструкция описывает создание следующей миграции,
  её проверку и применение, ограничения и безопасный порядок отката, штатный
  запуск приложения, а также оба пути подготовки БД: новую и существующую.
  README изменяется только в пределах этого миграционного порядка.
- Продуктовая модель, структура учебных данных и функциональность упражнений
  сохраняются. Соседние исправления и лишняя инфраструктура исключены.
- `docs/ARCHITECTURE.md` актуализируется по итоговой реализации после QA.

Применение любых изменений к действующей БД с данными учеников, включая
регистрацию версии и миграции, требует отдельного явного указания PO.

## Требования к QA

QA подключается после реализации и владеет всем тестовым кодом. Автоматизация
ограничена новой БД, штатным запуском backend и связанными ошибками. Переход
существующей схемы, созданной прежним `create_all`, не закрепляется автотестом:
для него достаточно ручной проверки на отдельной PostgreSQL с синтетическими
данными. Отдельный регрессионный автотест на пропуск индекса не требуется.

Минимальное окружение — отдельный PostgreSQL 15 в отдельном тестовом Compose-файле,
без подключения `database/data` и без изменения штатного Compose проекта.
Тестовый Compose использует `name: lingvar-migration-tests`, tmpfs для PostgreSQL,
не публикует host-порт и запускается командами с явным
`-p lingvar-migration-tests`; его остановка не вызывает `--remove-orphans` или
`--volumes` и не выполняется с обычным project name.
Backend запускается с явно заданным тестовым `DATABASE_URL`. Фикстуры требуют
отдельный `TEST_DATABASE_URL`, не берут обычный URL из `.env`, проверяют допустимое
тестовое имя; при ошибке прекращают работу до DDL. Сбрасывать разрешено только БД
этого тестового контейнера. Данные учеников и обычная БД приложения не используются.
Добавить только необходимые pytest/HTTP-зависимости и команду запуска; общий
браузерный контур ради миграций не создавать.

Связанные интеграционные проверки с общими фикстурами PostgreSQL, вызовами CLI
и backend с настоящим lifespan:

- Пустая БД: старт backend до миграций завершается ошибкой; `upgrade` создаёт
  все семь таблиц и initial revision, повторный `upgrade` ничего не меняет.
  После этого backend стартует. HTTP-сценарий регистрации/входа через существующий
  `/users/register` и `/users/token`, чтения слов и записи/чтения статистики
  подтверждает совместимость ORM с созданной схемой. Учебные записи синтетические.
- Старт отклоняет недоступную БД, отсутствующую, устаревшую и неизвестную версию.
  Штатный startup не вызывает `create_all`. Попытка отката initial не удаляет
  таблицы. Старый `backend/test_auth.py`, использующий обычную конфигурацию БД
  и создание таблиц, заменяется безопасными интеграционными проверками.

Ошибки validator/baseline и сохранность данных оцениваются по реализации и
результатам ручных проверок; отдельный автоматизированный контур перехода legacy
не создаётся. Если QA обнаружит конкретный дефект, передать его разработчику;
после исправления выполнить необходимую адресную проверку без автоматического
возврата исключённого legacy-сценария в набор автотестов.

## Комментарии к реализации

### Применимость и компоненты

Alembic подходит к существующему синхронному SQLAlchemy engine/psycopg2 и общей
`services.base.Base`. PostgreSQL 15 поддерживает транзакционный DDL, модели
используют штатный JSONB SQLAlchemy. Менять сессии, frontend, API или ORM-схему
для внедрения миграций не требуется. Проверка основана на исходниках
`backend/services/database.py`, `backend/models/user.py`,
`backend/models/vocabulary.py`, `backend/main.py`, Dockerfile и Compose;
фактическая схема действующей БД этим анализом не установлена.

- Добавить Alembic в `backend/requirements.txt`, стандартный
  `backend/alembic.ini` и `backend/migrations/{env.py,script.py.mako,versions/}`.
  URL берётся из `DATABASE_URL`, не хранится в ini; миграционные команды требуют
  явно заданный PostgreSQL URL и не используют SQLite fallback. Конфигурация
  и пути работают из backend и контейнера. Импорт моделей регистрирует metadata
  без импорта FastAPI-приложения и без создания таблиц.
- Закрепить `bcrypt==4.3.0` для совместимости существующего passlib 1.7.4
  при HTTP-проверке API на мигрированной БД; не менять сервис авторизации,
  формат хешей или продуктовый сценарий регистрации.
- Initial revision с фиксированным ID и `down_revision = None` содержит явные
  Alembic-операции создания существующих семи таблиц, индексов и FK в `public`.
  Никакого `create_all` или обращения к изменяемым ORM-моделям внутри revision.
  Сохранить текущие длины строк, JSONB, timezone, nullable, серверный `now()`,
  последовательности SERIAL и фактическую структуру индексов. Python `default`
  и `onupdate` не превращать в серверные defaults/триггеры. Initial после принятия
  неизменяемая; все следующие изменения — новые revisions. `uuid-ossp` не нужен
  ORM и не добавляется initial миграцией.
- Добавить компактный CLI `backend/migrate.py` и общий модуль
  `backend/services/migrations.py`: `python -m migrate upgrade`, `check`,
  `check-legacy`, `baseline`. CLI возвращает ненулевой код при любой ошибке,
  не выводит пароли и не исправляет схему автоматически. `upgrade` вызывает
  Alembic `upgrade head`; `check` только сверяет единственную текущую revision
  с единственной head из каталога миграций. Неизвестные revisions/несколько
  heads, пустая или многозаписная таблица версий отклоняются до DDL. Полный
  validator нужен для первичного перехода, а не при
  каждом запуске управляемой БД; прямые изменения управляемой схемы вне миграций
  эксплуатационная инструкция запрещает.
- `env.py` принимает переданный SQLAlchemy Connection через `Config.attributes`:
  общий CLI управляет транзакциями и блокировкой. Прямой `alembic upgrade head`
  также отклоняет непустую неуправляемую схему, вместо попытки применить initial
  поверх неё. Все миграционные Connection используют локальный `search_path`
  `public,pg_catalog`, чтобы неквалифицированный DDL initial и snapshot `public`
  относились к одной схеме. Прямой `alembic stamp` не является допустимым обходом: разрешить
  stamp только из проверенного пути `baseline`, с внутренним контекстом
  переданной транзакции. Не добавлять публичного `--force`.
- В lifespan `backend/main.py` удалить вызов `create_tables`, выполнить `check`
  перед `yield` и выбросить исключение при ошибке; Uvicorn тогда завершает startup.
  Сервис БД сохраняет engine/сессии; helper `create_tables` удаляется. Старый
  `backend/test_auth.py` заменяется безопасными проверками из раздела QA.

### Эталон и проверка legacy

`check-legacy` и `baseline` требуют отдельный явно заданный
`MIGRATION_REFERENCE_URL` на заранее подготовленную пустую disposable PostgreSQL
15. Её создание не входит в команды перехода. Это инфраструктура только для
сравнения и тестов, а не дополнительный сервис штатного запуска приложения.
Reference нельзя брать из обычной конфигурации или направлять на target.
Перед DDL проверить реально подключённые БД: разные имена БД обязательны,
reference имеет выделенное имя `lingvar_migration_reference` и не содержит
пользовательских объектов; никакой очистки непустой reference. Доступ к ней
выделяется оператором, отдельно от БД учеников. Выдать понятный отказ при
несовпадении версии PostgreSQL и параметров БД, влияющих на смысл сравнения
схемы (encoding, default locale/collation/provider).

На отдельном Connection reference начать транзакцию, применить Alembic только
до фиксированной initial revision, снять описание её `public`, затем всегда
откатить транзакцию: эталон снова пуст. Использовать тот же код чтения каталогов
для reference и target. Проверка целевой БД выполняет только SELECT; в неё
не создаются временная схема, таблицы или запись версии. Эталон не берётся
из текущей ORM, не является произвольной уже существующей БД и не получается
из одного результата autogenerate. Reference-транзакция и использование
reference сериализуются отдельной advisory-блокировкой.

Validator ограничен схемой initial и обнаружением дополнительных объектов,
а не универсальным преобразованием всех объектов PostgreSQL. Единый снимок
reference и target строится необходимыми SELECT к `pg_catalog`:

- Таблицы/колонки: имена, типы и параметры, timezone, nullable, серверные default,
  identity/generated, параметры сортировки (collation); неизвестные
  partitions/inheritance отклонять.
- PK/unique/FK: состав и порядок колонок, цели, действия ON DELETE/UPDATE,
  deferrability, validity. Проверить также отсутствие дополнительных CHECK,
  exclusion и иных ограничений, меняющих допустимые данные.
- Индексы: имя, состав/порядок, unique, метод, validity, predicate/expression,
  INCLUDE/opclass и параметры, если отличаются от обычного индекса initial.
  Учитывать индекс, принадлежащий PK/unique, один раз через его ограничение.
- SERIAL: имя и привязка последовательности к колонке, тип, шаг, границы, cycle
  и default `nextval`. Текущее значение последовательности является состоянием
  данных: не сравнивать с пустым эталоном, не вызывать `nextval`/`setval`.
- Выявлять дополнительные таблицы, views/materialized views, standalone sequences,
  types/functions/collations, triggers/rules/event triggers, RLS/policies и
  зависимости от других схем.
  Для views из других схем учитывать зависимости их rewrite rules от управляемых
  таблиц `public` в обоих направлениях.
  Не пытаться доказать их эквивалентность: неизвестное существенное свойство или
  неподдерживаемый объект — диагностика и отказ. Системные объекты и объекты
  известных расширений определяются по зависимостям каталога, а не по префиксу.

OID не включать в снимок. Типы читать через PostgreSQL `format_type`, выражения
defaults через `pg_get_expr`, ограничения через `pg_get_constraintdef`, индексы
через `pg_get_indexdef` при одном локальном `search_path` и совместимых locale/
encoding target и reference. Не удалять произвольные casts, скобки или кавычки
регулярным выражением ради «совпадения». Неизвестная эквивалентность выражения
даёт отказ, а не ложное разрешение. Сравнивать свойства и имена объектов, на которые следующие
миграции могут ссылаться; другие автоматически назначенные имена допускается
нормализовать только если доказано отсутствие таких ссылок. Порядок строк
каталога, OID, владельцы/GRANT и текущее содержимое таблиц не определяют равенство
схемы; ошибки доступа при проверке всё равно запрещают переход. Диагностика
содержит объект, свойство, ожидаемое и фактическое значение, без учебных данных.

### Переход и запуск

Для пустой БД: PostgreSQL готов → `python -m migrate upgrade` → запуск backend
и frontend. В Docker: `docker compose build backend`, `docker compose up -d
postgres`, `docker compose run --rm backend python -m migrate upgrade`,
`docker compose up -d backend frontend`. Эти команды — инструкция, а не
автоматически исполняемое действие над действующей БД.

Для legacy после отдельного указания PO на изменения:

1. Подготовить проверяемую резервную копию и отдельный пустой reference;
   не восстанавливать бэкап учеников в тесты. Выполнить read-only `check-legacy`
   с адресом нужной target и `MIGRATION_REFERENCE_URL`, изучить диагностику.
2. При расхождениях остановиться без stamp. По фактической структуре и данным
   подготовить конкретное сохраняющее данные исправление в рамках уточнения
   этой задачи, согласовать его с PO, проверить на синтетической воспроизводящей
   схеме и только по отдельному указанию применить к действующей БД. Неизвестные
   данные могут потребовать продуктового решения; универсальный конвертер
   не обещается. После исправления повторить `check-legacy`.
3. В окно обслуживания остановить старый backend и другие писатели; исключить
   все сторонние DDL-сеансы, в том числе администраторские. Выполнить `baseline`:
   одна target-транзакция, advisory-блокировка миграционных команд, блокировки
   существующих таблиц ACCESS EXCLUSIVE в стабильном порядке с `lock_timeout`,
   повторное чтение каталога и сравнение с заново полученным initial-эталоном,
   затем `stamp` именно initial ID на том же Connection и commit. При любой
   ошибке rollback оставляет target без изменений; таблицу версий заранее
   не создавать. Уже управляемая БД отклоняется без перерегистрации.
4. Выполнить явный `upgrade` до head, проверить состояние и запустить приложение.
   Если обновление не прошло, backend остаётся остановленным до решения ошибки.

Advisory-блокировка сериализует наши migration-команды; табличные блокировки
защищают проверенные таблицы до регистрации версии. Они не запрещают произвольное
создание нового объекта в `public` сторонним администратором. Поэтому исключение
стороннего DDL на всё окно baseline — обязательное условие этого решения;
разделённые `check-legacy` и обычный `stamp` его не заменяют. Команда `baseline`
не доверяет результату ранее запущенной проверки. `upgrade` использует ту же
advisory-блокировку и транзакционный путь; работающее приложение перед DDL
останавливается, автоматической миграции в lifespan/reload нет.

### Последующие миграции и откат

В README кратко описать: подготовить отдельную dev-БД до head, изменить ORM,
выполнить `alembic revision --autogenerate -m "..."` либо создать ручную revision,
проверить предложенный DDL и downgrade, прогнать upgrade и сценарии QA на
настоящей PostgreSQL, применить через явный `upgrade` перед запуском приложения.
Autogenerate требует ручного просмотра, особенно rename, defaults, constraints
и изменения с данными. Начальная migration не меняется вслед за ORM.

Initial `downgrade` явно отказывает: удаление всей схемы не является безопасным
откатом перехода. Не предоставлять автоматическое удаление версии после legacy
baseline. Для следующих revisions downgrade допустим только если автор явно
реализовал и проверил сохранение данных; иначе он должен отказывать. Откат
может требовать остановки приложения и восстановления заранее проверенной
резервной копии по отдельному указанию; `stamp` не откатывает структуру или данные.
Команды очистки/восстановления БД не являются частью обычного запуска и проверки.
По завершении QA актуализировать `docs/ARCHITECTURE.md` по реальным компонентам,
миграциям и устройству интеграционных проверок.

### Границы перехода

Миграции применяются явной командой перед стартом приложения; lifespan только
проверяет версию. Неизвестные дополнительные объекты в `public` и зависимости
вне него запрещают baseline. Исключение — системные объекты и установленное
существующим init расширение `uuid-ossp`, определённое по членству объектов
в расширении, если они не меняют учебные таблицы и не зависят от них.
Дополнительные колонки, ограничения и индексы учебных таблиц считаются расхождением.

При неизвестных расхождениях поставляется диагностируемый отказ без изменений.
Конкретное сохраняющее данные исправление согласуется внутри этой задачи после
обследования. До обследования успешный переход именно действующей БД не подтверждён.
