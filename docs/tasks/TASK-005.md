# Управление иерархией правил администратора

## Описание требований

Администратор управляет учебными правилами и их вложенной структурой. Доступ к
страницам и API управления правилами есть только у активного администратора;
ученик и неаутентифицированный посетитель не получают эти данные и операции.

В административной навигации есть переход к списку правил. Список показывает
верхнеуровневые правила и позволяет начать создание нового верхнеуровневого
правила, открыть его для редактирования и удалить его. Редактирование одного
верхнеуровневого правила открывает отдельную страницу, на которой одновременно
видно всё его дерево, без перехода на отдельные страницы его подправил. В этом
же редакторе администратор создаёт подправило у любого узла и продолжает
вложение на произвольную глубину, редактирует название и описание каждого
узла и может удалить узел.

У каждого правила обязательны непустые `title` и `description`. Название
ограничено существующим пределом данных в 200 символов; уникальность названий
не требуется. При создании и редактировании можно назначить родительское
правило либо сделать правило верхнеуровневым. Нельзя назначить родителем само
правило или любой его потомок: структура всегда остаётся деревом без циклов.
Ручное упорядочивание соседних правил не входит в задачу.

При сохранении или удалении интерфейс показывает результат операции, а при
ошибке (в том числе недоступность сервера, несуществующее правило, нарушение
валидации или ограничений иерархии) сохраняет введённые данные там, где это
применимо, и понятно сообщает, что изменения не сохранены. Удаление требует
подтверждения. При подтверждённом удалении правила его прямые потомки получают
родителя удаляемого правила; прямые потомки удаляемого верхнеуровневого правила
становятся верхнеуровневыми. Переназначение потомков и удаление правила
выполняются одной операцией: при ошибке не должно остаться частично изменённого
дерева.

Страница списка показывает карточку или строку каждого верхнеуровневого
правила: `title`, краткий фрагмент `description`, число непосредственных
подправил и действия «Редактировать» и «Удалить». Основное действие —
«Создать правило». При пустом списке вместо таблицы выводится пояснение и эта
же кнопка; для загрузки, ошибки получения данных и ошибки удаления есть
отдельные состояния с возможностью повторить запрос.

В шапке списка рядом с заголовком «Правила» всегда виден нейтральный счётчик
`Всего правил: N`, с пояснением «включая подправила». `N` — рекурсивная сумма
всех узлов леса, а не число карточек верхнего уровня и не только число их
прямых потомков. Счётчик строится из уже полученного дерева, обновляется после
каждой успешной мутации; в пустом состоянии показывает 0, при загрузке не
показывает устаревшее значение, при ошибке загрузки не выдаёт непроверенное
число за актуальное. На широком экране он стоит на одной строке с заголовком,
на узком — сразу под ним до поясняющего текста.

Карточки верхнеуровневых правил должны быть компактными по высоте: внутренние
отступы 12–16 px, интервал между карточками 8–12 px. В одной основной строке
показываются полужирный `title`, приглушённый счётчик непосредственных
подправил и компактные действия «Редактировать» и «Удалить»; описание —
второй строкой мелким приглушённым текстом, обрезанным после одной строки.
У действий сохраняется достаточная зона нажатия и текстовые подписи. На узком
экране содержимое карточки переносится: текст остаётся сверху, а действия
располагаются компактной строкой ниже без горизонтальной прокрутки; общий
счётчик при этом продолжает относиться ко всему дереву, а не к видимым
карточкам.

Создание открывает отдельную форму с обязательными полями названия и
многострочного описания и иерархическим селектором родителя; по умолчанию это
верхний уровень. Действие «Добавить подправило» в редакторе открывает такую же
пустую форму в панели свойств с заранее выбранным родителем. Отмена создания
возвращает к списку без сохранения.

Редактор на одном экране состоит из двух панелей: слева — дерево, справа —
свойства выбранного узла. Дерево показывает `title` каждого узла с отступом
по глубине; ветви с потомками можно развернуть или свернуть. Раскрытие ветви и
выбор узла являются отдельными действиями, выбранный узел заметно выделен.
Дерево сразу раскрывает путь к выбранному или только что созданному узлу.

```text
Правила / <верхнее правило>                     [Удалить правило]
<название верхнего правила>                     [Сохранить]
┌───────────────── дерево ─────────────────────┬──── свойства выбранного узла ───┐
│ ▾ <правило>                                  │ Название *                      │
│   ▾ <подправило>                             │ [..............................]│
│     • <вложенное условие>                    │ Описание *                      │
│   • <исключение>                             │ [многострочное поле............]│
│   [+ Добавить подправило]                    │ Родитель: [иерархический выбор]│
│                                              │ [Сохранить] [Удалить]           │
└──────────────────────────────────────────────┴─────────────────────────────────┘
```

Правая панель позволяет изменить `title`, `description` и родителя. Выбор
родителя исключает текущий узел и всё его поддерево. Для редактируемого
верхнеуровневого правила выбор родителя доступен, но при переносе в другое
дерево после сохранения редактор возвращается к исходному верхнеуровневому
дереву; перенесённый узел в нём больше не отображается. При несохранённых
изменениях переход к другому узлу предлагает сохранить или отменить их, чтобы
не потерять введённое. После создания подправило добавляется в раскрытую ветвь
и становится выбранным. При удалении листа правую панель переключается на
родителя; при удалении верхнеуровневого правила — на список.

Ошибки обязательных полей выводятся у соответствующих полей. На время запроса
кнопка сохранения недоступна; после успешного сохранения показывается краткое
подтверждение. Все действия имеют текстовые подписи, видимый фокус и достаточную
область нажатия. На узком экране дерево располагается над панелью свойств, без
горизонтальной прокрутки критичных действий.

Административный API расширяется следующими операциями под существующей
зависимостью активного администратора:

- `GET /admin/rules` возвращает весь лес правил в виде массива вложенных корневых
  узлов. Узел содержит `id`, `title`, `description`, `parent_rule_id`, внутренний
  `ordering` и `children`; потомки уже расположены в порядке отображения. Один
  ответ используется списком, редактором дерева и селекторами родителя, без
  отдельных запросов на каждый уровень.
- `POST /admin/rules` принимает `title`, `description` и необязательный
  `parent_rule_id`, создаёт верхнеуровневое правило или подправило и отвечает
  созданным узлом со статусом 201.
- `PUT /admin/rules/{rule_id}` принимает полный набор этих же изменяемых полей,
  обновляет один узел и отвечает обновлённым узлом.
- `DELETE /admin/rules/{rule_id}` выполняет согласованное удаление с переносом
  прямых потомков и при успехе отвечает без тела со статусом 204.

API обрезает окружающие пробелы в `title` и `description`, после чего проверяет
их непустоту и ограничение `title` в 200 символов. Несуществующие изменяемое
правило или родитель дают 404, попытка выбрать себя или потомка родителем — 409,
ошибки полей — 422. Для неаутентифицированного посетителя сохраняется 401,
для ученика — 403. Ответы об ошибках содержат понятный `detail`, который frontend
может показать без подмены успешного состояния; ошибка записи в БД возвращает
контролируемый 500 после rollback.

Проверка иерархии на backend является окончательной: при изменении родителя
рекурсивный запрос проверяет всё поддерево изменяемого узла, а не только прямых
детей. Все `POST`, `PUT` и `DELETE` до чтения, валидации и записи выполняют
`LOCK TABLE rules IN SHARE ROW EXCLUSIVE MODE`, чтобы две одновременные допустимые
по отдельности операции не смогли совместно образовать цикл или получить один
и тот же порядок. После ошибки транзакция откатывается.

При создании и переносе узел автоматически добавляется в конец выбранного уровня.
При удалении прямые потомки добавляются одним блоком после уже существующих детей
прежнего родителя (либо после существующих корней), сохраняя взаимный порядок.
Поле `ordering` остаётся внутренним: ручное изменение через API и интерфейс не
предоставляется. Для старых строк с одинаковым или пустым `ordering` сервер
использует устойчивую дополнительную сортировку по `title`, затем `id`.

Существующая таблица `rules` уже содержит обязательные `title`, `description`,
nullable self-reference `parent_rule_id`, индекс родителя и `ordering`, поэтому
новая миграция и изменение модели данных не требуются. Удаление реализуется как
одна серверная транзакция: после блокировки целевое правило и родитель повторно
проверяются, прямым потомкам назначаются новый родитель и порядок, затем удаляется
сам узел и выполняется один `commit`. Ограничение внешнего ключа остаётся
последней защитой; при любой ошибке перенос потомков также откатывается.

Frontend добавляет маршруты `/admin/rules`, `/admin/rules/new` и
`/admin/rules/[rootId]`, ссылку «Правила» в административной навигации и
типизированные методы API. Страница редактора строит дерево из одного ответа
`GET /admin/rules`, но показывает только поддерево корня из URL; селектор родителя
может использовать остальные деревья из того же ответа. Если корень из URL не
существует или перестал быть корневым вне текущего действия, показывается
понятное состояние с возвратом к списку.

Несохранённое состояние хранится отдельно от последнего ответа API. При попытке
выбрать другой узел или покинуть редактор предлагаются действия «Сохранить»,
«Не сохранять» и «Остаться»; неуспешное сохранение оставляет пользователя и
введённые значения на месте. После каждой успешной мутации лес запрашивается
заново, чтобы UI не воспроизводил серверные правила переноса самостоятельно.
Если не корневой узел перенесён в другое дерево, редактор остаётся в исходном
дереве и выбирает его корень; если перенесён сам открытый корень, редактор
переходит к верхнеуровневому корню дерева назначения и выбирает перенесённый
узел. После удаления некорневого узла выбирается его прежний родитель, а после
удаления корня выполняется переход к списку правил.

## Требования к QA

Расширить существующие интеграционные наборы, не создавая unit-тестов и не
подключая штатную БД учеников.

В backend-сценарии поверх отдельной настоящей PostgreSQL одним связанным потоком
проверить административный CRUD: создать корень, несколько уровней и соседние
ветви, прочитать вложенный лес, изменить текст, перенести узел между ветвями и
сделать его корнем. Проверить 422 для пустых после обрезки обязательных полей,
404 для отсутствующего правила или родителя и 409 для назначения родителем себя
или потомка; после каждого отказа прочитать дерево и подтвердить отсутствие
изменений. Для `GET`, `POST`, `PUT` и `DELETE` проверить 401 без токена и 403
с токеном ученика.

В том же backend-наборе удалить промежуточный узел и подтвердить, что только его
прямые потомки получили прежнего родителя, а более глубокие связи сохранились;
затем удалить корень и подтвердить превращение его прямых потомков в корни.
Атомарность отказа проверить на настоящей тестовой БД, временно установив
тестовый PostgreSQL-trigger, который отклоняет удаление целевого правила после
выполнения переназначения: API должен вернуть ошибку, а повторное чтение и прямой
запрос БД — показать исходного родителя у потомков и наличие удаляемого узла.

Браузерный сценарий расширить полным позитивным путём администратора: открыть
список, создать корень и вложенность не менее трёх уровней, увидеть полное дерево
на одной странице, свернуть/раскрыть ветвь, изменить выбранный узел, создать
подправило из панели, перенести узел и подтвердить удаление с ожидаемым новым
деревом. На списке проверить рекурсивный общий счётчик в пустом и многоуровневом
дереве, его пересчёт после удаления корня с повышением потомков и отсутствие
непроверенного значения при ошибке загрузки. Проверить сохранение введённых
значений при серверной ошибке и защиту несохранённой формы при смене узла.
Существующий сквозной сценарий доступа должен по-прежнему подтверждать, что
посетитель перенаправляется на вход, ученик видит отказ на административных
маршрутах, а учебные маршруты ученика не регрессировали.
