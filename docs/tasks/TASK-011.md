# Форматируемые описания и просмотр правил учеником

## Описание требований

Поле `rules.description` становится HTML-фрагментом с ограниченной разметкой.
Имя поля и тип `Text` в БД не меняются, отдельное поле с исходным или plain-text
вариантом не создаётся. Допустимы только:

- абзац и перенос строки: `p`, `br`;
- жирное, курсивное и подчёркнутое начертание: `strong`, `em`, `u`;
- маркированные и нумерованные списки: `ul`, `ol`, `li`;
- таблица без заголовочных ячеек: `table`, `tbody`, `tr`, `td`;
- размер фрагмента текста 14 или 20 px через `span data-font-size="14"` и
  `span data-font-size="20"`; обычный размер 16 px хранится без отметки размера.

Другие теги и любые другие атрибуты запрещены. В частности, не допускаются
`style`, `class`, `id`, обработчики событий, ссылки, изображения, заголовки,
цвета, внешние ресурсы, `iframe`, произвольные `data-*`, объединение ячеек и
заголовочные ячейки таблицы. Обычный текст без тегов допустим. Ссылкоподобный
текст остаётся текстом и автоматически не превращается в ссылку.

Backend является границей доверия для HTML. Общий сервис правил должен разбирать
фрагмент HTML, проверять теги, атрибуты и допустимые значения
`data-font-size`, очищать и канонически сериализовать его библиотекой HTML-
санитизации с явным allowlist; регулярные выражения не используются как
санитайзер. При `POST/PUT /admin/rules` сервис молча удаляет запрещённые теги,
атрибуты и недопустимые значения `data-font-size`, канонизирует оставшийся
безопасный фрагмент и сохраняет именно результат очистки; наличие неподдерживаемой
разметки само по себе не даёт `422`. Ответ API также содержит сохранённое
каноническое значение. При формировании административных и ученических проекций
тот же allowlist повторно очищает копию значения без изменения БД, чтобы
существующая или некорректно внесённая строка также не могла попасть в браузер
как непроверенная разметка. Комментарии и служебные артефакты редактора удаляются.
После очистки описание должно содержать видимый текст: пустые абзацы, одни
переносы, неразрывные пробелы, полностью удалённая запрещённая разметка и пустая
таблица не считаются описанием и дают структурированную ошибку `422` поля
`description`. Только в этом случае существующая запись и дерево не изменяются.

Санитизация и операции с деревом (единая сортировка по `ordering`, затем title
и id, поиск корня и построение поддерева с защитой от цикла) выделяются в общий
backend-сервис и переиспользуются admin CRUD, ученическим API и снимками сессий.
Для серверной санитизации добавляется специализированная поддерживаемая
библиотека, например `nh3`; frontend-фильтрация не заменяет серверную проверку.
Изменение схемы и Alembic-миграция не нужны: `Text` уже хранит HTML, а снимок
сессии находится в JSONB. Массового преобразования существующих строк нет;
безопасность их выдачи обеспечивает общий сервис, а ближайшее сохранение
переводит строку в канонический формат.

В административной форме обычный `textarea` заменяется клиентским редактором
на Tiptap с двумя режимами одного черновика, оформленными как доступные вкладки
«Визуально» и «HTML». Новая или выбранная запись открывается во вкладке
«Визуально». Визуальный режим предоставляет только следующие действия:

- абзац, жирный, курсив, подчёркнутый текст;
- маркированный и нумерованный список;
- выбор 14, 16 или 20 px, где 16 px — значение по умолчанию и удаляет отметку
  размера;
- вставка таблицы выбором сетки от 1×1 до 5×5.

Ненужные возможности Tiptap, включая headings, strike/code, blockquote,
автоссылки, изображения, цвета и header cells, отключаются. Пользователь может
редактировать текст в созданных ячейках, но toolbar не добавляет операций
объединения ячеек и заголовков. Вставка из буфера приводится к той же схеме;
сервер остаётся окончательной проверкой. Таблица в визуальном редакторе имеет видимые
границы и внутренние отступы всех ячеек, включая ещё пустые ячейки; эти стили не
записываются в HTML.

Вкладка «HTML» содержит моноширинный `textarea` с исходным HTML текущего черновика. При
переходе из визуального режима она получает актуальную сериализацию Tiptap. Ввод в ней
сразу изменяет `description` как буквальную строку: разметка не очищается, не исправляется и
не канонизируется на каждом нажатии. Защита несохранённых изменений учитывает raw-редактирование.

При переходе из HTML-режима во вкладку «Визуально» буквальный черновик молча фильтруется по
действующей схеме разрешённых тегов, атрибутов и значений `data-font-size`: `style`, обработчики,
произвольные `data-*` и неподдерживаемые элементы/атрибуты не попадают в результат. Переход не
блокируется и отдельная ошибка запрещённой HTML-разметки в интерфейсе не показывается. Tiptap получает
отфильтрованный фрагмент, после чего общий `description` заменяется его актуальной канонической
сериализацией. Поэтому буквальный вариант с запрещённой разметкой после перехода не сохраняется.

Сохранение непосредственно из HTML-режима сначала выполняет ту же фильтрацию и каноническую
сериализацию, синхронизирует ими общий черновик и скрытый визуальный редактор и только затем отправляет
очищенное значение существующему API. После успешного ответа форма принимает каноническое значение
backend. Если после фильтрации описание не содержит видимого текста, применяется обычная ошибка
обязательного поля; это не ошибка конкретного тега. Backend остаётся авторитетной границей безопасности
и повторяет ту же allowlist-очистку даже для прямого API-запроса. Обычная серверная ошибка показывается
в общей области `description`; к этому моменту черновик уже содержит отфильтрованное, а не первоначальное
буквальное значение.

Редактор корректно загружает сохранённый HTML, передаёт его через существующее поле `description`,
связывает единственную видимую редактируемую область и общую ошибку через `aria-invalid`/
`aria-describedby` и участвует в существующей защите несохранённых изменений без ложного dirty-
состояния сразу после загрузки. Вкладки имеют семантику `tablist`/`tab`/`tabpanel` и клавиатурно доступное
переключение. Кнопки toolbar имеют понятные `aria-label`/tooltip, активные состояния `aria-pressed` там, где
применимо, видимый focus ring и область нажатия не менее 40×40 px.

Активные состояния toolbar вычисляются заново при каждой транзакции и смене курсора или выделения
в Tiptap, а не остаются снимком предыдущего render. Для курсора кнопка нажата согласно формату в текущей
позиции; для непустого выделения она нажата только когда соответствующий формат покрывает всё выделенное
содержимое. Смешанное выделение (например, часть жирная, часть обычная или части с разными размерами)
не помечает ни один неоднородный формат как активный. Размер 16 px считается активным только при едином
отсутствии mark размера.

Pointer-нажатие на кнопку toolbar не должно оставлять DOM selection и `TextSelection` ProseMirror
рассинхронизированными. Для inline-команд — жирного, курсива, подчёркивания и размеров шрифта — обработчик
`pointerdown` до возможной смены фокуса только сохраняет текущие ProseMirror `from`/`to` и предотвращает
стандартный перенос фокуса; сам документ на этой фазе не меняется. Поскольку браузерное `selectionchange`
после клавиатурного выделения может ещё не успеть обновить `editor.state.selection`, pointer-обработчик
берёт anchor/focus фактического native selection, пока оба находятся внутри DOM редактора, переводит их
в позиции документа публичным `editor.view.posAtDOM` и сохраняет нормализованные `from`/`to`
`TextSelection`. Native selection при этом только читается, но не изменяется. Если валидного DOM-выделения
в редакторе нет, используется актуальный `editor.state.selection`. Внутренний `view.domObserver` и его
`flush` не используются как недокументированный API. Последующий `click` применяет mark к
захваченному диапазону, синхронно возвращает фокус вызовом `editor.view.focus()` и после этого восстанавливает
тот же `TextSelection` командой ProseMirror/Tiptap. `editor.commands.focus()` для этого порядка не используется:
в React он откладывает фактический `view.focus()` до `requestAnimationFrame`, поэтому немедленно выполненный
следом `setTextSelection` ещё работает с редактором без DOM-фокуса, а клавиатурное событие после `click` может
успеть попасть в кнопку toolbar. Для клавиатурной активации, у которой нет `pointerdown`, тот же `click`
использует актуальный диапазон из `editor.state.selection`. Native DOM `Range` вручную не создаётся и не подставляется:
после изменения mark структура текстовых DOM-узлов может измениться, а параллельное управление native
selection обходит синхронизацию ProseMirror и снова создаёт два конкурирующих источника состояния.
Это восстановление не применяется к структурным командам абзаца, списков и таблицы. Поэтому после
форматирования выделенного текста первого пункта маркированного списка последующая клавиатурная навигация
работает по текущей позиции и не очищает первый `li`.

Быстро следующие друг за другом клавиши навигации не должны зависеть от того, успел ли браузер отправить
`selectionchange` между `keydown`. В `editorProps.handleKeyDown` редактор синхронно воспроизводит стандартную
семантику двух используемых комбинаций через транзакции ProseMirror: `ArrowRight` без модификаторов при
непустом `TextSelection` схлопывает его в `selection.to`, а `Ctrl+End` переводит курсор в
`TextSelection.atEnd(doc)`. Обработанные события возвращают `true`, поэтому browser default не создаёт
параллельное DOM-only состояние; остальные клавиши идут обычным путём редактора. Обрабатывать только
`ArrowRight` недостаточно: между browser-default `Ctrl+End` и следующим `Enter` остаётся та же гонка.

При фактическом выборе другого правила в дереве, создании подправила или переходе после подтверждения
несохранённых изменений экземпляр редактора предыдущей логической записи снимает фокус, очищает DOM/
ProseMirror selection и демонтируется до загрузки нового черновика. Поэтому браузерное выделение и состояние
toolbar не переносятся между правилами; фокус после обычного выбора остаётся на нажатой кнопке дерева, а редактор
не перехватывает его. Открытие диалога несохранённых изменений само по себе не меняет редактор: действие
«Остаться» возвращает к прежнему черновику, режиму и выделению без сброса.

В списке верхнеуровневых правил HTML не показывается строкой с тегами: краткий preview строится как
безопасный plain text.

Frontend содержит один read-only-компонент форматированного описания, общий для
подсказки и страницы правила. Он получает только очищенный сервером HTML и
выводит его с едиными стилями абзацев, вложенных списков, размеров и таблиц.
Каждая широкая таблица прокручивается по горизонтали внутри собственной области,
не расширяет popover или страницу; границы и отступы ячеек остаются читаемыми.
На странице базовый размер описания 16 px, в popover — компактные 14 px, при этом
явно выбранные размеры 14/20 сохраняют смысл. Вызов `dangerouslySetInnerHTML`
сосредоточен только в этом компоненте и не применяется к произвольным строкам.

Снимок `fill_blanks` по-прежнему фиксирует на момент создания сессии выбранное
для пропуска правило и всё его упорядоченное поддерево. Формат
`content.rule_hints[blank_id]` дополнительно содержит `root_rule_id` — id корня,
к которому выбранное правило относилось при создании сессии. Само дерево снимка
содержит только title, очищенный `description` и children; id выбранного узла,
definition упражнения и правильные ответы в ученическую проекцию не попадают.
Редактирование правила после начала упражнения не меняет текст или
`root_rule_id` существующего снимка. Временные снимки старого контракта не
адаптируются и не backfill-ятся.

В ученической проекции новой сессии два или более непосредственно соседних
`blank` без части `text` между ними показываются одним полем, если текстовая
подсказка `hint` отсутствует у всех этих пропусков либо задана только у последнего.
Подсказка последнего пропуска сохраняется в проекции `blank_group.hint` и
показывается рядом с общим полем так же, как возле одиночного пропуска. Подсказка
у любого более раннего пропуска является границей группы: объединение через неё
не выполняется, а после неё может начаться следующая подходящая группа. Часть
`text`, в том числе содержащая только пробелы, также всегда разделяет группы.
Это представление рассчитывается только при создании новой сессии; сохранённые
сессии не преобразуются.

Общее поле меняет только представление и способ отправки ответа. В
`blank_group.blanks` остаются упорядоченные `id` и `word_count` каждого пропуска,
а ответы, число попыток, статусы, история, правило и снимок правила продолжают
храниться отдельно по `blank_id`. Проверка общего поля использует существующее
действие `fill_blank_group_check`, распределяет слова по `word_count` и не
смешивает независимый прогресс пропусков.

После закрытия пропуска существующий hover/focus popover показывает
форматированное снимковое дерево. После каждого самостоятельного дерева находится
ссылка «Открыть правило» на `/rules/{root_rule_id}`; поэтому у объединённого поля
со снимками нескольких правил ссылка есть в каждом соответствующем разделе.
Popover остаётся ограниченным по высоте и прокручиваемым, а таблица имеет свою
горизонтальную прокрутку. Поскольку внутри появился интерактивный элемент,
панель оформляется как немодальный интерактивный popover, а не ARIA-tooltip:
trigger сообщает `aria-expanded`/`aria-controls` и наличие popover, панель имеет
доступное имя. Наведение или фокус на trigger открывает её; перевод указателя или
клавиатурного фокуса на панель и ссылку не закрывает её; Escape и уход фокуса/
указателя за весь компонент закрывают. Focus ring видим, область ссылки не менее
40 px по высоте; focus trap не нужен.

Для общего поля popover собирается из `content.rule_hints` его пропусков в том же
порядке, что и `blank_group.blanks`, и показывает снимки уже закрытых пропусков
последовательно, один под другим. Снимки не объединяются и не удаляются как
дубликаты: разные назначенные правила являются отдельными секциями со своим
деревом и своей ссылкой «Открыть правило» на соответствующий `root_rule_id`.
Частично закрытая группа показывает только снимки уже закрытых пропусков; после
закрытия всей группы доступны все её снимки. Текстовая `hint` последнего пропуска
не заменяет и не скрывает снимки правил.

Ширина popover ограничена меньшим из 32 rem и ширины viewport за вычетом
горизонтальных полей по 1 rem. Это ограничение задаётся валидным CSS-выражением
`min(32rem, calc(100vw - 2rem))`: пробелы вокруг оператора `-` обязательны,
иначе браузер отбрасывает всё значение и содержимое с `width: max-content`
растягивает панель. Панель и контейнеры деревьев могут сжиматься до этой ширины.

Обычное содержимое описания в popover не создаёт горизонтальную прокрутку:
абзацы, элементы списков и весь их inline-текст (`span`, `strong`, `em`, `u`,
текст возле `br`), включая длинные слова или непрерывные строки, переносятся
внутри доступной ширины панели. Таблицы являются единственным исключением:
широкая таблица сохраняет собственную локальную горизонтальную прокрутку, но не
растягивает сам popover и не заставляет прокручивать его целиком.

Добавляется отдельный ученический router `GET /api/rules/{rule_id}`, защищённый
`get_current_student_user`. Для существующего корня или подправила он находит
актуальный корень и возвращает безопасную проекцию всего актуального поддерева:

```json
{
  "canonical_rule_id": 10,
  "rule": {
    "id": 10,
    "title": "...",
    "description": "<p>...</p>",
    "children": []
  }
}
```

Каждый дочерний узел имеет те же `id`, `title`, `description`, `children`;
порядок совпадает с административным деревом. Запрос подправила возвращает
`canonical_rule_id` её корня и всё дерево корня. Несуществующий id даёт `404`,
анонимный запрос — `401`, администратор — `403`. Endpoint не раскрывает
упражнения, их definition, ответы или административные поля правила. Отдельных
`GET /api/rules` и ученического каталога правил нет.

Создаётся защищённая клиентская страница `/rules/[ruleId]`, а маршрут добавляется
к учебным маршрутам `RoleRouteGuard`. Она загружает описанную проекцию; если
`canonical_rule_id` отличается от параметра URL, выполняет
`router.replace('/rules/{canonical_rule_id}')` и не показывает дерево до
канонизации адреса. На каноническом адресе страница выводит корень как `h1` и его
форматированное описание, затем всё дерево подправил в серверном порядке,
полностью раскрытым и без элементов сворачивания. Уровни имеют семантические
заголовки и визуальное различие вложенности, но сохраняют читаемую ширину на
мобильном экране. Предусмотрены состояния загрузки, повторяемой ошибки связи и
отдельное состояние «правило не найдено». Неавторизованного посетителя guard
направляет на вход, администратора — в `/admin`. Ссылки на страницу есть только
в подсказках: пункт общей навигации и страница `/rules` со списком не создаются.

## Требования к QA

Backend-интеграционный сценарий на настоящей тестовой PostgreSQL расширяется так,
чтобы одной связной проверкой подтвердить:

- создание и изменение правила сохраняет канонический HTML для всех разрешённых
  групп разметки, включая оба списка, размеры 14/20 и обычную таблицу;
- `script`, ссылка/изображение, `style`, `on*`, чужой `data-*`, неподдерживаемый
  тег и неверный `data-font-size` молча удаляются прямым административным API;
  разрешённая часть сохраняется канонически и возвращается в ответе. Если после
  очистки видимого текста не остаётся, API даёт `422` по `description` и не
  меняет сохранённую запись;
- ученический `GET /api/rules/{id}` возвращает упорядоченное полное дерево,
  очищенные описания и один canonical root как для корня, так и для глубокого
  подправила; проверяются `401`, запрет администратору `403` и `404`;
- новая сессия `fill_blanks` содержит безопасный неизменяемый снимок поддерева и
  `root_rule_id`, не содержит definition/ответов/id выбранного подправила, а
  последующее редактирование актуального правила меняет ученическую проекцию
  правила, но не снимок уже созданной сессии;
- сериализация новой `fill_blanks`-сессии объединяет соседние пропуски без
  подсказок и соседние пропуски с `hint` только у последнего, возвращая у группы
  эту последнюю подсказку. Подсказка раньше последнего и любая часть `text`
  разрывают группу; в проекцию по-прежнему не попадают принимаемые ответы;
- проверка такой группы сохраняет отдельные состояния, попытки и историю каждого
  `blank_id`, в том числе при частично правильном ответе; снимки разных правил
  остаются отдельными значениями `rule_hints` в порядке пропусков.

Эти проверки добавляются в существующие сценарии правил и упражнений с повторным
использованием их пользователей, БД и helpers; отдельные unit-тесты санитайзера
не создаются. Миграционный тест не добавляется, поскольку схема БД не меняется.

Browser-сценарий с настоящими backend и БД проверяет полный пользовательский
путь: администратор создаёт через WYSIWYG корневое правило и подправило, применяет
начертания, список, размер и таблицу, сохраняет и повторно открывает редактор;
существующая защита несохранённого rich-text ввода продолжает работать. Ошибка
поля `description`, возвращённая backend, сохраняет введённое содержимое,
показывается рядом с редактором и связана с редактируемой областью через
`aria-invalid` и `aria-describedby`. Ученик
закрывает связанный пропуск, с клавиатуры открывает popover, видит форматирование
и доступную ссылку, переводит на неё фокус без закрытия панели и переходит на
страницу правила. Страница показывает полный раскрытый root/subrule tree и
форматирование; переход по прямому URL глубокого подправила заменяет адрес на
корневой до показа содержимого. Проверяются локальная горизонтальная прокрутка
таблицы на узком viewport, not-found и ролевой доступ страницы.

В этом же ученическом сценарии отдельная регрессия создаёт два или более соседних
пропуска с подсказкой только у последнего и разными назначенными правилами. На
странице это одно поле, рядом с ним видна последняя текстовая подсказка. После
частичного закрытия его popover содержит только снимки закрытых пропусков, а после
полного закрытия — отдельные секции всех снимков в порядке пропусков и отдельную
ссылку каждого дерева. Сценарий также подтверждает, что подсказка раньше
последнего или часть `text` между пропусками не позволяют получить одно общее
поле.

Browser-регрессия использует эквивалент реального HTML, на котором обнаружен
дефект: длинный польский абзац с несколькими `strong`, пустой абзац, абзац с
`em` и абзац с несколькими жирными строками через `br`. На desktop viewport
открытый popover имеет ширину не более 32 rem, абзац занимает несколько строк,
а панель и её обычное содержимое не имеют горизонтального переполнения. Проверка
должна измерять фактические `clientWidth`/`scrollWidth`, а не только наличие CSS-
класса, чтобы не пропустить недействительное вычисляемое ограничение ширины.

В том же сценарии на узком viewport описание содержит обычный абзац, список и
длинное неразрывное слово: текст переносится, а ширина панели не превышает
viewport за вычетом горизонтальных полей по 1 rem. Существующая проверка широкой
таблицы сохраняется: таблица переполняется и прокручивается только в собственной
области, сам popover не получает горизонтальной прокрутки.

Тот же административный browser-сценарий покрывает регрессии редактора:

- переход «Визуально» → «HTML» показывает текущую сериализацию, буквальное
  редактирование HTML помечает форму изменённой, сохраняется через backend и
  после повторного открытия отображается в обоих режимах;
- переход «HTML» → «Визуально» с запрещёнными тегом и атрибутом не блокируется и
  не показывает ошибку разметки: неподдерживаемые части молча удаляются, а
  разрешённый текст и форматирование отображаются и становятся новым черновиком;
- сохранение непосредственно из HTML-режима с такой же смешанной разметкой
  отправляет очищенный канонический HTML, после повторного открытия запрещённые
  части отсутствуют в обоих режимах. Если фильтрация оставляет описание без
  видимого текста, показывается обычная ошибка обязательного поля;
- вставленная таблица имеет различимые границы и размеры даже у пустых ячеек;
- перемещение курсора между жирным и обычным текстом сразу меняет
  `aria-pressed` кнопки, а смешанное выделение не показывает жирный или размер
  шрифта как однородно активный;
- после выделения текста в одном правиле выбор другого правила через дерево
  убирает прежнее выделение, показывает toolbar нового содержимого и оставляет
  фокус на кнопке дерева. Если при изменённом черновике пользователь выбирает
  другое правило и нажимает «Остаться», текущий режим, черновик и выделение не
  сбрасываются.
- В одном последовательном сценарии выделяется текст первого `li` маркированного списка и к тому же
  выделению через toolbar по очереди применяются жирный, курсив, подчёркивание и размер шрифта. После каждого
  `click` активным элементом снова является редактируемая область ProseMirror; проверка только наблюдает
  `activeElement` и сама не вызывает `focus`. Затем без нового click выполняется
  `ArrowRight → Ctrl+End → Enter → Backspace`, и оба исходных `li` сохраняются. Клавиши после toolbar
  отправляются через `page.keyboard`, а не `locator.press()`: последний сам фокусирует contenteditable
  и скрывает рассинхронизацию фокуса и selection.

QA обновляет существующие browser helpers, которые вводили описание через
`textarea`, для работы с WYSIWYG и не дублирует одинаковую подготовку rich-rule
дерева между сценариями. Полный набор действующих backend- и browser-проверок
запускается после изменений.

## Комментарии к реализации

Tiptap подключается только в клиентском компоненте редактора, совместимом с
Next.js App Router. Набор extension-ов ограничивается описанной схемой; размер
текста реализуется собственным mark/attribute `data-font-size`, а не произвольным
inline CSS. Для HTML-режима используется браузерный разбор DOM и единая frontend-
функция allowlist-фильтрации, общая для перехода в визуальный режим и подготовки
payload при сохранении. Она молча удаляет неподдерживаемую разметку, затем Tiptap
даёт каноническую сериализацию; две операции не должны расходиться и позволять
сохранению обойти фильтр. Новая frontend-зависимость для этого не требуется.

Жизненный цикл Tiptap привязывается не только к строке `value`, а к идентичности
редактируемой записи/сессии формы: ключ меняется только при применённом переходе
на другое правило или создании нового черновика. Простая отмена pending-перехода
ключ не меняет. Перед заменой выполняются blur и очистка selection, затем прежний
editor уничтожается; загрузка нового содержимого не вызывает `onChange` и не
создаёт ложное dirty-состояние. Активное состояние панели подписывается на
транзакции/selection Tiptap и для непустого диапазона проверяет полноту покрытия
mark, включая атрибут размера, а не наличие mark хотя бы в части диапазона.
Границы таблиц задаются CSS, ограниченным визуальной областью редактора, и не
добавляют разрешённые атрибуты в сохраняемый фрагмент.

Схема БД, миграции, маршруты и формы DTO для этого уточнения не меняются;
write-поведение административного API меняется со строгого отказа на очистку и
сохранение безопасного результата.
Учебный API читает актуальное дерево из `rules`, тогда как popover намеренно
читает только JSONB-снимок сессии: объединять эти два источника нельзя.

Learner DTO и соответствующий frontend-тип `blank_group` получают поле
`hint: string | null`. Сериализатор `fill_blanks` сканирует части слева направо,
не меняя административный `definition`: часть `text` и подсказка не в последней
позиции завершают текущего кандидата, а подходящая последовательность из двух и
более пропусков превращается в одну группу. Содержимое `rule_hints`, серверный
answer key, структура `progress.blanks` и контракт действия группы не меняются.

Frontend выводит `blank_group.hint` возле общего input и связывает её с полем для
доступного чтения. Для popover он выбирает снимки по упорядоченным `blank_id`
группы и статусам их независимого progress, а не по наличию текстовой подсказки.
Сам popover получает валидное ограничение inline-размера меньшим из 32 rem и
`calc(100vw - 2rem)`; сочетание с размером по содержимому не может отменить эту
границу. В Tailwind arbitrary value пробелы CSS-выражения кодируются символами
`_`, то есть класс должен дать браузеру вычисляемое значение с пробелами вокруг
`-`, а не прежнее недействительное `calc(100vw-2rem)`. Стили общего read-only-компонента задают обычный перенос и
`overflow-wrap: anywhere` для `p`, `li` и их inline-содержимого, включая
`span`/`strong`/`em`/`u` и строки с `br`, не применяя это ограничение к структуре
таблицы. Контейнеры дерева имеют `min-width: 0` и могут сжиматься до ширины
popover, а `table` остаётся отдельным блоком с `max-width: 100%` и локальным
`overflow-x: auto`.
