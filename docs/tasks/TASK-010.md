# Подсказки правил и история ответов в пропусках

## Описание требований

Изменение относится только к учебному экрану упражнения типа `fill_blanks` и к текущей сессии ученика.

После закрытия пропуска правильным ответом либо после исчерпания попыток и показа правильного ответа ученик может навести указатель на это поле или перевести на него клавиатурный фокус и увидеть всплывающую подсказку с правилом. Для пропуска с явным сопоставлением показывается это правило; иначе — правило, назначенное упражнению (не его верхний предок в дереве). Подсказка содержит название и описание выбранного правила, а ниже — все его подправила с названиями и описаниями, в структуре и порядке дерева правил. Подправила включаются рекурсивно на всех уровнях. Подсказка не модальная, размещается рядом с trigger-ом, имеет ограничение высоты с прокруткой при длинном дереве и не перекрывает вводимое значение; Escape закрывает её. Закрытое поле остаётся фокусируемым, но недоступным для изменения, чтобы эта подсказка была доступна с клавиатуры.

Существующий стек из трёх точек индикатора попыток становится единственным trigger-ом истории соответствующего пропуска: по наведению или клавиатурному фокусу он показывает немодальную всплывающую историю его введённых ответов в текущей сессии, в порядке ввода. Сам trigger — кнопка с доступным именем «История ответов для пропуска N»; цветные точки внутри неё остаются декоративными. История имеет заголовок «История ответов» и упорядоченный список дословно введённых проверенных значений; при отсутствии таких значений сообщает «Пока нет проверенных ответов». В историю попадают только ответы, для которых сервер выполнил проверку; не попадают пустой ввод, несостоявшаяся из-за сетевой или серверной ошибки проверка и повторный устаревший запрос. История сохраняется при восстановлении той же сессии и очищается при «Начать заново».

Подсказки открываются при hover или focus, закрываются при уходе указателя и фокуса из trigger-а и самой подсказки, а также по Escape; при Escape фокус остаётся на исходном поле или индикаторе. Они не заменяют существующее текстовое объявление статуса результата. У trigger-ов есть видимое контрастное focus ring, а содержимое подсказки программно связано с trigger-ом.

Для объединённого поля нескольких соседних пропусков оно остаётся доступным, пока открыт хотя бы один пропуск. При hover или focus такого поля правило показывается для каждого уже закрытого входящего пропуска: если закрыт один, это обычная подсказка его правила; если их несколько, единый popover перечисляет их в порядке пропусков с метками «Пропуск N» и отдельным деревом правила у каждой метки. Открытые пропуски в подсказку не включаются. История по-прежнему относится к одному пропуску и открывается только его собственным расположенным рядом стеком точек. Таким образом, общее поле не создаёт неоднозначного trigger-а истории и не мешает вводу ответов в ещё открытые пропуски.

Данные подсказок и истории входят в снимок серверной сессии, а не загружаются frontend отдельно из административного API. При создании `fill_blanks`-сессии backend для каждого пропуска выбирает его собственное `rule_id` либо `exercise.rule_id`, читает выбранный узел и всех его потомков и сохраняет безопасную ученическую проекцию дерева: `title`, `description` и рекурсивный `children`. Массивы `children` следуют тому же стабильному порядку, что административное дерево: заданный `ordering`, затем название и ID как разрешение пустых или одинаковых значений порядка. В публичном `content` сессии появляется отображение `rule_hints` по ID пропуска на корень такого дерева; в нём нет административного definition упражнения, `accepted_answers`, серверного ключа ответов и иных скрытых данных. Все ответы создания, восстановления и действий используют только эту публичную проекцию.

Дерево правила копируется в JSONB-состояние в момент создания сессии. Поэтому уже начатая сессия показывает прежнюю формулировку и структуру после редактирования дерева администратором и после перезапуска backend; новая сессия получает актуальное дерево. Это продолжает существующую семантику неизменяемого снимка упражнения. Изменение таблиц и миграция не нужны.

Контракт действует для сессий, созданных актуальной версией приложения: в их `fill_blanks`-снимке `rule_hints` и `answer_history` обязательны. Обратная совместимость с JSONB-снимками, созданными до появления этих полей, в объём задачи не входит; frontend и backend не содержат fallback, backfill или специального восстановления таких сессий.

Каждое состояние пропуска `fill_blanks` в `progress.blanks` дополнительно содержит массив `answer_history`. Backend добавляет запись только внутри успешно выполняемого, изменяющего состояние проверочного действия после проверки ожидаемого числа попыток. Для одиночного пропуска сохраняется исходная непустая строка `answer`, без trim, изменения регистра и замены уже сохранённых значений. Для объединённого поля каждому ещё открытому пропуску записывается его непустой фрагмент в том виде, в котором сервер выделил этот фрагмент и проверил его согласно сохранённому `word_count`; закрытые пропуски, лишние нераспределённые слова и пустой фрагмент записи не получают. Полный текст общего поля не дублируется в историях отдельных пропусков. Устаревшее повторное действие целиком остаётся идемпотентным: не меняет историю, прогресс и revision. Ошибка до commit не оставляет историю благодаря той же транзакции, что сохраняет попытку. Восстановление сессии возвращает массивы из JSONB; restart удаляет прежнюю сессию и создаёт новую с пустыми историями.

Типизированный frontend-контракт сессии отражает `rule_hints` и `answer_history`; эти поля относятся только к варианту `fill_blanks`. Renderer строит правило исключительно из снимка сессии и не обращается к `/admin/rules`. Для закрытых полей используется `readOnly`, а не `disabled`, чтобы значение нельзя было изменить, но само поле оставалось в порядке Tab и могло быть trigger-ом подсказки; временно ожидающее ответа поле по-прежнему может быть `disabled`. Закрытое объединённое поле ведёт себя так же, а частично закрытое остаётся редактируемым.

Общую механику popover следует выделить в переиспользуемый frontend-компонент или локальный компонент renderer-а: уникальные ID содержимого, связь через ARIA, открытие по pointer hover и focus, удержание при переходе указателя или фокуса между trigger-ом и содержимым, закрытие после ухода из обеих областей и по Escape без переноса фокуса. Закрытие по Escape не должно немедленно переоткрывать popover из-за всё ещё сфокусированного trigger-а; повторное открытие происходит после нового hover/focus-входа. Компонент не переносит прогресс в локальное постоянное состояние: после каждого ответа источником остаётся новый серверный снимок. Дерево правила выводится рекурсивным представлением, сохраняющим вложенность; длинное содержимое ограничено по высоте и прокручивается внутри popover.

## Требования к QA

Расширить существующий backend-интеграционный сценарий упражнений на настоящей тестовой PostgreSQL, не создавая отдельного unit-контура. В одном связном сценарии создать многоуровневое дерево с явно сопоставленным и несопоставленным пропусками и проверить:

- снимок содержит для каждого пропуска выбранное правило и всех потомков в стабильном рекурсивном порядке, но нигде не раскрывает `accepted_answers` или серверный ключ правильных ответов;
- изменение названия, описания или структуры правил после создания сессии не меняет её create/get/action DTO, тогда как новая сессия получает актуальное дерево;
- одиночные неверные и правильные проверки добавляют исходные непустые значения в правильном порядке; устаревший повтор запроса не добавляет дубль и не увеличивает revision;
- групповая проверка добавляет каждому открытому пропуску только фактически проверенный непустой фрагмент, не добавляет историю уже закрытому пропуску и сохраняет частичный прогресс атомарно;
- get после нового `TestClient`/перезапуска приложения возвращает то же дерево и историю из PostgreSQL, а restart выдаёт другой ID с пустой историей;
- отклонённый пустой одиночный ввод и серверная ошибка с rollback не создают запись истории. Сетевую ошибку покрыть в браузерном сценарии, поскольку запрос в этом случае не достигает backend.

Расширить существующий Playwright-сценарий `fill_blanks` поверх backend и тестовой PostgreSQL, переиспользуя его подготовку пользователя, упражнения и проверки попыток. Проверить отображение подсказки правила для явного и унаследованного сопоставления, включая несколько уровней и порядок подправил, а также историю ответов текущей сессии. История должна дословно показывать проверенные одиночные значения, не включать ввод при перехваченной сетевой ошибке, переживать reload и очищаться после «Начать заново».

Проверить оба trigger-а с клавиатуры: закрытое поле доступно по Tab, но не редактируется; кнопка точек имеет имя «История ответов для пропуска N», цветные точки скрыты от accessibility tree, содержимое связано с trigger-ом, focus ring видим, Escape закрывает popover и сохраняет фокус. Hover/focus между trigger-ом и popover не должен закрывать его преждевременно; существующий `aria-live`-статус результата остаётся доступен.

В grouped-сценарии закрыть сначала один пропуск: поле остаётся редактируемым, правило показывает только закрытый пропуск, а его кнопка точек показывает только его историю. После закрытия второго пропуска единый popover поля выводит обе секции «Пропуск N» в порядке пропусков и отдельное дерево каждой; обе истории остаются доступны только через собственные кнопки точек. После полного закрытия общее поле остаётся фокусируемым `readOnly` trigger-ом. Существующие backend- и browser-интеграционные проверки сессий запускаются целиком для контроля регрессий.
