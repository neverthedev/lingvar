# Изолированный контур интеграционных тестов

## Описание требований

Довести до требуемого минимального контура уже добавленное в TASK-001 тестовое
окружение, не создавая второй параллельный контур. В его состав уже входят
отдельный Compose-проект и disposable PostgreSQL, явное применение текущей
Alembic-схемы, защита тестового DDL по `TEST_DATABASE_URL` и документированная
команда запуска. Их необходимо сохранить как единственный способ запуска
интеграционных проверок backend и при необходимости исправить только фактическое
расхождение с требованиями этой задачи.

Использовать существующий `docker-compose.test.yml`: Compose-проект должен иметь
общее имя `lingvar-tests` в `name:` и во всех командах `-p`; сервис
`postgres-test` создаёт PostgreSQL 15 с нейтральным именем БД `lingvar_test`
и учётной записью `lingvar_test_user` на `tmpfs`, без host-порта; healthcheck
обращается к `lingvar_test`. `backend-tests` подключён только к этому
Compose-проекту и получает совпадающие тестовые `TEST_DATABASE_URL` и
`DATABASE_URL`, указывающие на `lingvar_test`. Не подключать к нему
сервисы, сеть, том `database/data` или credentials из штатного `docker-compose.yml`.
Внешний запуск тестов без этого выделенного Compose-проекта не является
поддерживаемым способом проверки.

Тестовая PostgreSQL остаётся полностью отделённой от штатной: не использует её
URL, учётные записи, тома, сеть Compose или данные учеников. Перед каждым тестом
и после него очищать только схему `public` выделенной disposable тестовой БД,
после проверки имени БД, серверной версии PostgreSQL 15 и подключённой тестовой
учётной записи. Схему учебных таблиц затем применять только явной штатной
командой `python -m migrate upgrade`; автоматическое `create_all` запрещено.
Тест жизненного цикла миграций начинает с пустой схемы и сам проверяет отказ
backend до `upgrade`; HTTP-сценарии выполняют `upgrade` до запуска FastAPI
`TestClient`. Каждый тест должен быть независим от оставшихся записей и порядка
запуска, включая одиночный запуск.

В `README.md` описать воспроизводимый запуск из корня репозитория командой
`docker compose -p lingvar-tests -f docker-compose.test.yml
up --abort-on-container-exit --exit-code-from backend-tests --build backend-tests`:
Compose поднимает одноразовую PostgreSQL, pytest очищает её перед каждым тестом,
затем тест явно применяет текущую миграцию и выполняет проверки. Указать команду
`docker compose -p lingvar-tests -f docker-compose.test.yml down` для
завершения только тестового проекта и пояснить, что подготовка схемы происходит
внутри тестов, а не при старте обычного backend.

`README.md` описывает только актуальный штатный запуск и общий интеграционный
контур. Удалить устаревшие разделы о переходе существующей БД (включая
`check-legacy`, `baseline`, reference-БД и команды с `MIGRATION_REFERENCE_URL`)
и о последующих миграциях/откате, а также финальное упоминание ручной проверки
legacy-схемы в разделе тестов. Это изменение пользовательской инструкции;
миграционный CLI и его legacy-валидацию не удалять.

Актуализировать фактическую карту `docs/ARCHITECTURE.md`, чтобы она описывала
новое общее имя и нейтральное имя тестовой БД. Описание существующего
миграционного кода в карте сохраняется как описание фактической реализации,
без инструкции к переходу БД учеников. Файлы завершённых задач не изменять.

Контур предназначен для backend сейчас и не должен препятствовать последующему
добавлению браузерного сценария «вход → упражнение → сохранение → повторное
открытие». Браузерный раннер, frontend-тесты и настройки запуска frontend в этой
задаче не создаются. Не добавлять миграции, unit-тесты, проверки всех API,
административного API или изменения продуктовой функциональности. Не выполнять
восстановление, очистку либо иные действия с обычной БД учеников.

## Требования к QA

QA сопровождает интеграционные проверки backend с настоящей отдельной тестовой
PostgreSQL. Основной HTTP-сценарий после применения текущей схемы использует
только синтетические данные в тестовой БД и последовательно проверяет:

- успешную регистрацию нового пользователя и вход;
- авторизованный запрос к существующему учебному API;
- сохранение результата упражнения через существующий API и его фактическое
  наличие в БД для зарегистрированного пользователя.

Под результатом упражнения здесь понимаются уже реализованные результаты
табличных упражнений: получение учебного слова и авторизованные запросы
`/api/tests`, сохраняющие `word_test_stats`. Отдельные страницы из `/api/exercises`
сейчас не сохраняют результаты; требовать их сохранения означало бы менять
продуктовую функциональность и выходит за границы задачи.

Отдельный тест проверяет повторную регистрацию с теми же данными и подтверждает,
что второй пользователь не появился. Этот ошибочный сценарий не должен быть
частью основного сценария. Существующие проверки жизненного цикла миграций
сохраняются; задача не требует расширять их новыми несвязанными случаями.

Структура тестов: в `backend/tests/conftest.py` оставить общую защиту URL,
engine и сброс `public`, но сделать подготовку/очистку БД изолированной для
каждого теста вместо одного сброса на весь набор. До любого DDL проверять
`TEST_DATABASE_URL`: PostgreSQL, имя БД `lingvar_test`, host `postgres-test` и
пользователя `lingvar_test_user`; после подключения сверять `current_database()`,
`current_user` и PostgreSQL 15. Перед импортом backend в тестах установить
`DATABASE_URL` равным проверенному `TEST_DATABASE_URL`, не наследуя обычный URL
из окружения. `services.database` создаёт engine при импорте, поэтому общий
fixture устанавливает тестовый URL до выполнения тестов, а первый импорт `main`
выполняется внутри теста после установки URL; тест отказа при недоступной БД
меняет `DATABASE_URL` лишь после этого импорта и восстанавливает его сразу после
проверки. По завершении теста вернуть прежнее значение переменной.

В `backend/tests/test_migrations.py` оставить проверки пустой/обновлённой схемы,
lifespan, повторного `upgrade`, запрета downgrade/stamp и недоступной БД;
извлечь оттуда проверки регистрации, входа и статистики. В отдельном файле
`backend/tests/test_user_workflow.py` создать два интеграционных HTTP-теста:
основной связный сценарий и отказ повторной регистрации. Оба теста начинают со
своей пустой тестовой схемы, явно вызывают `python -m migrate upgrade` и затем
используют `TestClient(app)` с настоящими SQLAlchemy-сессиями без подмены `get_db`.
Основной сценарий создаёт одно синтетическое существительное с обязательными
JSONB-формами, регистрирует пользователя, входит через `/users/token`, проверяет
`/users/me` и авторизованную выдачу `/api/nouns/single`, затем отправляет
`/api/tests/attempt` и `/api/tests/complete`. После закрытия HTTP-клиента он
читает `word_test_stats` напрямую в этой тестовой БД по `user_id`, `word_type`
и `word_id` и проверяет сохранённые число попыток/успехов, завершение и время.
Тест повторной регистрации отдельно создаёт пользователя через HTTP, повторяет
тот же запрос, проверяет ожидаемый 400 и общее количество строк `users`, равное
одному на своей пустой схеме. Синтетические записи подготавливать в тесте, а не
предполагать наличие учебных данных в БД; случайный порядок выдачи не должен
влиять на результат.

После переименования Compose-проекта и тестовой БД повторить документированный
полный запуск backend-интеграционных тестов на выделенной PostgreSQL и
подтвердить, что новый проект не подключает штатные сервисы, сеть и том.
HTTP-сценарии не перерабатывать ради смены имени БД; QA меняет только
соответствующую защиту и фикстуры в общем тестовом коде.

## Комментарии к реализации

В тестовом Compose задать `name: lingvar-tests`, сменить `POSTGRES_DB`, цель
healthcheck и обе переменные URL на `lingvar_test`. Штатный Compose, схема,
миграции, frontend и зависимости остаются прежними. Имеющиеся initial revision,
`pytest` и `httpx` из `backend/requirements-test.txt` достаточны. Разработчик
обновляет `README.md` и запускает существующие проверки; он не создаёт и не редактирует тесты либо вспомогательный
тестовый код. Изоляцию фикстур и композицию HTTP-тестов реализует QA. Он же
обновляет константу разрешённого имени БД в `backend/tests/conftest.py` и
повторяет полный запуск после смены имени. Если существующая проверка падает
из-за несвязанного дефекта, разработчик исправляет реализацию, а ожидаемые
падения из-за согласованной перестройки тестов передаёт QA с объяснением.
По итогам архитектор обновляет `docs/ARCHITECTURE.md` с фактическим устройством
общего тестового контура.
